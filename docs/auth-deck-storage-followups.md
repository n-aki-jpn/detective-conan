# 認証・サーバー側デッキ保存：不足・未実装項目

作成日: 2026-11-25
対象コミット: `fcb118b`（認証・ユーザー管理とサーバー側デッキ保存の追加）

本ドキュメントは、ニックネーム認証＋Bearerトークン＋サーバー側ユーザーデッキ保存の実装後に残っている既知の不足点・未実装項目を一覧化したものである。

---

## 1. セキュリティ関連（重要度: 高）

| # | 項目 | 現状 | 対応案 |
|---|------|------|--------|
| S1 | パスワード/PIN認証がない | ニックネーム一致のみでログイン可能。ニックネームを知る誰でもそのユーザーになりすませる | パスワードまたは4桁PINの追加、またはハッシュ化した秘密文字列の併用 |
| S2 | トークンの保存先がlocalStorage | XSS発生時にトークンが窃取されるリスク | HttpOnly + Secure + SameSite Cookie方式への移行 |
| S3 | ログイン・登録のレート制限なし | ニックネーム総当たりが可能 | IP／ニックネーム単位の試行回数制限、指数バックオフ |
| S4 | HTTPS前提の設定なし | 平文HTTPではトークンが盗聴される | リバースプロキシ（Caddy/Nginx）でのTLS終端、`Secure`属性 |
| S5 | `/api/logs` が無認証で公開 | 対戦ログ（手札情報を含む可能性）が誰でも取得できる | 認証必須化、またはログのマスキング・ルーム別アクセス制御 |
| S6 | CORS・ヘッダー設定なし | 同一オリジン前提。今後別オリジン配信時に未整備 | tower-http CORS設定の明示 |

## 2. アカウント管理（重要度: 中）

| # | 項目 | 現状 | 対応案 |
|---|------|------|--------|
| A1 | ログアウト用APIがない | フロントがローカルのトークンを消すだけで、サーバー側セッションは有効期限まで残り続ける | `POST /api/logout`（トークン無効化）の追加 |
| A2 | アカウント削除機能なし | ユーザー自身・管理者ともに削除手段なし | `DELETE /api/me`（全セッション・デッキ削除）、管理者用削除 |
| A3 | ニックネーム変更機能なし | 登録後に変更できない | `PUT /api/me`（重複チェック付き変更） |
| A4 | アカウント復旧手段なし | メール・合言葉等がなく、ニックネームを忘れたら復旧不能 | 復旧用シードコードの発行 |
| A5 | ニックネーム正規化が未実施 | 大文字/小文字、全角/半角、前後空白以外の空白種別が別物扱い | NFKC正規化・大小無視の重複判定 |

## 3. デッキ同期・保存（重要度: 中）

| # | 項目 | 現状 | 対応案 |
|---|------|------|--------|
| D1 | localStorageが依然としてビルダーの作業コピー | サーバー→ローカル復元は「ローカルに存在しないデッキ」のみ。複数デバイスで同名デッキを編集するとズレる | サーバーを唯一の真実とし、ビルダー読み込みを `/api/decks/:id` ベースに変更 |
| D2 | 同期が一方向・欠損のみ | デバイスAでの変更がデバイスBの既存デッキに反映されない | `updatedAt` による最終書き込み優先のマージ、または明示的な再取得 |
| D3 | 削除がfire-and-forget | `deleteCurrentDeckSlot()` のサーバー削除は失敗を握りつぶす | 結果を確認し、失敗時に再試行・エラー表示 |
| D4 | 初回移行失敗時の再試行UIなし | 移行は初回ログイン時に一度だけ（失敗時は再試行されるが、ユーザーへの通知なし） | 移行結果のトースト通知、手動再移行ボタン |
| D5 | デッキの共有（ユーザー間）がない | 公式発行コード（タカラトミー）経由のみ | 共有コードによるユーザー間デッキ受け渡し |
| D6 | アクティブデッキがグローバル | `deck.json` / `deck_def` は全ユーザー共有。`isActive` 判定やデフォルトルームのデッキがユーザー単位でない | ユーザー単位のアクティブデッキ保存（`active_deck_id`） |
| D7 | ソドルームがグローバルデッキを使用 | `solo_*` ルーム生成時に `mgr.deck_def`（全体共通）をコピーするため、複数ユーザー同時利用時に他ユーザーのデッキで開始しうる | ソドルーム生成時にそのユーザーのアクティブデッキを使用 |
| D8 | オンラインP2参加時のfallbackがグローバルデッキ | `handle_join_room` の `sanitize_deck` fallbackが `mgr.deck_def` | 参加者本人のアクティブデッキをフォールバックに |

## 4. データ層・運用（重要度: 中）

| # | 項目 | 現状 | 対応案 |
|---|------|------|--------|
| O1 | ファイルベース永続化 | `users.json` / `sessions.json` / デッキJSON。グローバルMutex前提でスケールしない | SQLite等への移行（並行書き込み・トランザクション） |
| O2 | セッションクリーンアップの遅延 | 期限切れセッションは「次のトークン解決時」までファイルに残る | 起動時・定期タスクでの削除 |
| O3 | バックアップ戦略なし | `data/dummy/user_decks` 等のバックアップ手順が未文書化 | 定期バックアップ手順のドキュメント化 |
| O4 | ユーザー数・利用統計なし | 登録数・アクティブ数を追跡していない | 集計エンドポイントまたはログ出力 |

## 5. テスト（重要度: 中）

| # | 項目 | 現状 | 対応案 |
|---|------|------|--------|
| T1 | HTTPハンドラの認証統合テストなし | `UserManager` の単体テストのみ。401/403/400 のエンドポイント挙動を未検証 | `axum::test` + `tower::ServiceExt` での統合テスト |
| T2 | 移行APIの冪等性テストなし | `migrate_user_decks` の重複・presetスキップをテストで担保していない | 移行テストの追加（既存deckIdスキップ、preset_スキップ） |
| T3 | 他ユーザーデッキへのアクセス拒否テストなし | `user_B` が `user_A` のデッキを get/delete できないことを検証していない | ルーム間分離のテスト追加 |
| T4 | フロントエンドのE2Eテストなし | ログイン→移行→保存→再ログインの一連フローを手動確認のみ | Playwright等のE2E導入 |

## 6. UX（重要度: 低）

| # | 項目 | 現状 | 対応案 |
|---|------|------|--------|
| U1 | 登録/ログインの切り分けが曖昧 | 「ログイン」で存在しないニックネームはエラーになり、新規登録への誘導が手動 | 未登録時自動で登録にフォールバック、または統合ボタン |
| U2 | 同一ブラウザで複数アカウント切替の導線が弱い | ログアウト→再ログインのみ | アカウント一覧からのクイック切替 |
| U3 | セッション期限切れの事前通知なし | 7日後に突然401でログイン画面 | 使用前の自動リフレッシュ（スライディングTTL） |
| U4 | デッキ一覧に「サーバー保存済み」表示がない | ローカル保存とサーバー保存の区別がUI上ない | 保存状態バッジ（☁️等）の表示 |

---

## 対応優先度の提案

1. **S1（パスワード/PIN）**: 現状のニックネームのみ認証は実質的なアクセス制御ではなく、公開運用前に必須
2. **S2/S4（トークン安全・TLS）**: 公開ドメインで運用する場合に必須
3. **D1/D6（サーバー正・ユーザー別アクティブデッキ）**: 複数ユーザー同時運用時のデータ混線防止
4. **T1〜T3（統合テスト）**: 認証まわりのリグレッション防止
5. **A1/A2（ログアウト・アカウント削除API）**: 公開運用時の最低限の自己管理機能
